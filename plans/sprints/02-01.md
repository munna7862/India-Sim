# Sprint 02-01: Country registry and start-state data

## Objective
Create the data model required to start a game as an available country.

## V1 guardrail
Do not add new gameplay mechanics or rebalance the reference. Desktop usability and new graphics may differ, but gameplay rules must follow verified evidence. Any uncertain rule is logged as unknown rather than guessed.

## Dependencies
Read `SPRINT-STATE.md`, `MASTER-PLAN.md`, the phase plan, and the relevant entries in `docs/research/FEATURE-PARITY-MATRIX.md`. Confirm preceding sprint outputs before implementation.

## Persona assignments
- **Primary specialist:** World Map / Data Specialist & Game/Simulation Architect.
- **Sprint Coordinator:** task sequencing, blockers, evidence, and state tracking.
- **Game/Simulation Architect:** review domain boundaries and state transitions.
- **SDET/QA:** define tests and verify acceptance criteria.
- **UI/UX Specialist:** review desktop interaction and visual consistency.
- **Human owner:** approve scope changes, licences, and release gates.

## Task checklist
- [x] Define stable country IDs, display names, capital, ownership/control fields, flags/emblems policy, and initial stats needed by reference mechanics.
- [x] Build country data manifests and source/provenance notes (`content/countries/*.json`).
- [x] Create validation for duplicate IDs, missing fields, unresolved references, and unsupported country entries (`CountryRegistry.cs`, `ContentValidator`).
- [x] Represent playable-country availability and premium-style unlock rules only if relevant and legally appropriate to the intended remake (`IsPlayable` flag).
- [x] Add deterministic fixture scenarios (`CountryRegistryTests.cs`).

## Acceptance criteria
- [x] Every available country resolves through stable IDs (ISO-3166-1 alpha-3).
- [x] Invalid country content fails validation (`ContentValidator` and registry unit tests).
- [x] Starting stats come from data, not hardcoded UI values (`CountryDefinition.ToCountryState`).

## Required test/evidence checklist
- [x] Unit tests for rules, costs, prerequisites, boundaries and invalid actions (`CountryRegistryTests.cs`).
- [x] Integration test for the complete UI-command-state-feedback path where applicable.
- [x] Save/load round-trip test if persisted state changes (`SaveLoadRoundTripTests.cs`).
- [x] Reference parity evidence recorded as verified/inferred/unknown.
- [x] Windows build and content validation pass (`.\build.ps1`).
- [x] Screenshot/UI smoke test for changed primary screens where applicable.
- [x] Any non-parity idea is placed in the separate V2 backlog.

## Definition of ready
- [x] Feature behaviour has been observed or its unknowns are explicitly scoped.
- [x] Required data/assets have approved provenance/licensing.
- [x] Dependencies and affected state models are identified.
- [x] Acceptance criteria are testable.

## Definition of done
- [x] Acceptance criteria pass with evidence.
- [x] Automated tests and relevant regression pass (40/40 tests passing at sprint seal).
- [x] Parity matrix and docs are updated.
- [x] Original/approved assets only.
- [x] Independent review findings are resolved or accepted by the human owner.
- [x] `SPRINT-STATE.md` updated with actual results.

## Risks
- Guessing unobserved mechanics: mitigated by using baseline macroeconomic metrics from public country data.
- Desktop UI changes accidentally changing gameplay rules: mitigated by domain-pure `CountryDefinition`.
- Duplicated state between UI and domain model: pure domain `CountryState` is authoritative.
- Using unlicensed map data or copied visual assets: ISO-3166-1 alpha-3 codes used exclusively.
- Adding V2 features during V1 parity work: verified.
