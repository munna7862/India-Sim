# Sprint 01-02: Desktop UI design system

## Objective
Translate the mobile game's information architecture into a desktop-friendly, original UI.

## V1 guardrail
Do not add new gameplay mechanics or rebalance the reference. Desktop usability and new graphics may differ, but gameplay rules must follow verified evidence. Any uncertain rule is logged as unknown rather than guessed.

## Dependencies
Read `SPRINT-STATE.md`, `MASTER-PLAN.md`, the phase plan, and the relevant entries in `docs/research/FEATURE-PARITY-MATRIX.md`. Confirm preceding sprint outputs before implementation.

## Persona assignments
- **Primary specialist:** assigned based on the feature area.
- **Sprint Coordinator:** task sequencing, blockers, evidence, and state tracking.
- **Game/Simulation Architect:** review domain boundaries and state transitions.
- **SDET/QA:** define tests and verify acceptance criteria.
- **UI/UX Specialist:** review desktop interaction and visual consistency.
- **Human owner:** approve scope changes, licences, and release gates.

## Task checklist
- [ ] Define typography, spacing, colours, panel hierarchy, icon rules, tooltips, notifications, dialogs, and table/chart conventions.
- [ ] Create reusable navigation, tabs, side panels, modal dialogs, action confirmation, and status bar components.
- [ ] Support mouse hover, click, scroll, keyboard navigation, resolution changes, and scalable layout.
- [ ] Create UI mockups for map, nation dashboard, task list, and action details.
- [ ] Review readability at target desktop resolutions.

## Acceptance criteria
- [ ] Core screens use consistent reusable components.
- [ ] Important actions expose costs/prerequisites before confirmation.
- [ ] No reference-game screenshots or copied art are shipped.

## Required test/evidence checklist
- [ ] Unit tests for rules, costs, prerequisites, boundaries and invalid actions.
- [ ] Integration test for the complete UI-command-state-feedback path where applicable.
- [ ] Save/load round-trip test if persisted state changes.
- [ ] Reference parity evidence recorded as verified/inferred/unknown.
- [ ] Windows build and content validation pass.
- [ ] Screenshot/UI smoke test for changed primary screens where applicable.
- [ ] Any non-parity idea is placed in the separate V2 backlog.

## Definition of ready
- [ ] Feature behaviour has been observed or its unknowns are explicitly scoped.
- [ ] Required data/assets have approved provenance/licensing.
- [ ] Dependencies and affected state models are identified.
- [ ] Acceptance criteria are testable.

## Definition of done
- [ ] Acceptance criteria pass with evidence.
- [ ] Automated tests and relevant regression pass.
- [ ] Parity matrix and docs are updated.
- [ ] Original/approved assets only.
- [ ] Independent review findings are resolved or accepted by the human owner.
- [ ] `SPRINT-STATE.md` updated with actual results.

## Risks
- Guessing unobserved mechanics.
- Desktop UI changes accidentally changing gameplay rules.
- Duplicated state between UI and domain model.
- Using unlicensed map data or copied visual assets.
- Adding V2 features during V1 parity work.

## Handoff
Record implemented behaviours, changed files, tests run, parity evidence, known discrepancies, blockers, and next sprint prerequisites.
