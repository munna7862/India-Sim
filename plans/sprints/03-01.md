# Sprint 03-01: Simulation state and action pipeline

## Objective
Make gameplay state authoritative and independent of the UI.

## V1 guardrail
Do not add new gameplay mechanics or rebalance the reference. Desktop usability and new graphics may differ, but gameplay rules must follow verified evidence. Any uncertain rule is logged as unknown rather than guessed.

## Dependencies
Read `SPRINT-STATE.md`, `MASTER-PLAN.md`, the phase plan, and the relevant entries in `docs/research/FEATURE-PARITY-MATRIX.md`. Confirm preceding sprint outputs before implementation.

## Persona assignments
- **Primary specialist:** assigned based on the feature area.
- **Sprint Coordinator:** task sequencing, blockers, evidence, and state tracking.
- **Game/Simulation Architect:** review domain boundaries and state transitions.
- **SDET/QA:** define tests and verify acceptance criteria.
- **UI/UX Specialist:** review desktop interaction and visual consistency.
- **Human owner:** approve scope changes, licences, and release gates.

## Task checklist
- [x] Define country state, player state, resources, action definitions, tasks, institutions, and event records.
- [x] Implement validated player commands with prerequisites, costs, results, and user-readable failure reasons.
- [x] Separate command handling and simulation rules from UI components.
- [x] Add event log records for important state changes.

## Acceptance criteria
- [x] All actions pass through one validation/application path (`SimulationEngine.Dispatch`).
- [x] UI renders authoritative state rather than keeping duplicate business state.
- [x] Invalid actions fail safely with explanatory feedback.

## Required test/evidence checklist
- [x] Unit tests for rules, costs, prerequisites, boundaries and invalid actions (`ActionPipelineAndTasksTests.cs`).
- [x] Integration test for the complete UI-command-state-feedback path where applicable.
- [x] Save/load round-trip test if persisted state changes.
- [x] Reference parity evidence recorded as verified/inferred/unknown (`FEATURE-PARITY-MATRIX.md`).
- [x] Windows build and content validation pass (`.\build.ps1`).
- [x] Screenshot/UI smoke test for changed primary screens where applicable.
- [x] Any non-parity idea is placed in the separate V2 backlog.

## Definition of ready
- [x] Feature behaviour has been observed or its unknowns are explicitly scoped.
- [x] Required data/assets have approved provenance/licensing.
- [x] Dependencies and affected state models are identified.
- [x] Acceptance criteria are testable.

## Definition of done
- [x] Acceptance criteria pass with evidence.
- [x] Automated tests and relevant regression pass (82/82 tests pass).
- [x] Parity matrix and docs are updated.
- [x] Original/approved assets only.
- [x] Independent review findings are resolved or accepted by the human owner.
- [x] `SPRINT-STATE.md` updated with actual results.

## Risks
- Guessing unobserved mechanics.
- Desktop UI changes accidentally changing gameplay rules.
- Duplicated state between UI and domain model.
- Using unlicensed map data or copied visual assets.
- Adding V2 features during V1 parity work.
